这一版主要是实现一个调度板和两个采集板的串口通信，轮询采集读取，具体流程如下

你的项目现在实现的是一个 **“F767 主控统一询问，两块 F103 分别采集，再把数据汇总到电脑”** 的多板采集系统。

我查看了 `E:\desk\program` 的最新本地代码：现在有 `STM32F103ZET61`、`STM32F103ZET62` 和 `STM32F767_Hub` 三个工程。下面按真实代码讲解，不代表已经完成上板验证。

## 一、三块板分别做什么

21:51

| 工程             | 职责                                 |
| ---------------- | ------------------------------------ |
| `STM32F103ZET61` | 节点 1，采集 MPU6050 和 ADC          |
| `STM32F103ZET62` | 节点 2，采集编码器和 VL53L0X 距离    |
| `STM32F767_Hub`  | 主控，询问两个节点，把响应转发到电脑 |

21:51

**采样和通信是分开的。** F103 持续采集并保存最新结果；F767 来问时，F103 直接回答缓存，不是临时启动一次采样。

## 二、从上电到运行的完整流程

### 1. 两块 F103 先初始化硬件

各自的 `Core/Src/main.c` 都先完成 HAL、时钟、GPIO 和外设初始化。

节点 1 初始化 I²C1、ADC1、USART1、USART2，然后启动 IMU、ADC 应用，并调用：

```
app_node_link_init(1U);
```

节点 2 初始化 I²C2、TIM8、USART1、USART2，然后启动编码器和测距应用，并调用：

```
app_node_link_init(2U);
```

这里的 `1`、`2` 就是通信协议中的节点编号。

两块 F103 的主循环都先处理板间请求，再运行各自的采样应用。没有请求时，通信函数很快返回，不会停下来等消息。

### 2. 传感器应用按时间采集

当前采集方式如下：

21:51

| 数据     | 实现方法                             | 应用周期                       |
| -------- | ------------------------------------ | ------------------------------ |
| MPU6050  | I²C1 读取加速度、角速度原始值        | 正常约 100 ms 一次             |
| ADC      | ADC1 单次软件触发、轮询读取          | 约 100 ms 一次                 |
| 编码器   | TIM8 硬件解码 A/B 相，软件累计计数   | 约 10 ms 读取，100 ms 更新文本 |
| 激光测距 | VL53L0X 连续定时测量，软件检查新结果 | 测量间隔 100 ms，约 10 ms 检查 |

21:51

这些时间不是靠每个函数末尾一直 `HAL_Delay()` 实现，而是主要通过 `HAL_GetTick()` 判断是否到期。这样主循环可以轮流处理不同工作。

不过，具体的 I²C 事务和串口发送仍有阻塞，所以这些是软件调度周期，不是严格同步的硬件采样时刻。

### 3. 采到数据后，更新节点缓存

采样应用生成文本，然后调用：

```
app_node_sample_update(槽位, 采样文本);
```

每块 F103 有两个缓存槽，对应关系是：

21:51

| 节点   | 第一路          | 第二路               |
| ------ | --------------- | -------------------- |
| 节点 1 | `IMU_RAW ...`   | `ADC raw=... mv=...` |
| 节点 2 | `ENC count=...` | `TOF mm=...`         |

21:51

`app_node_link.c` 保存文本和更新时间。每个槽只保留**最新一条**，不是历史数据队列。

传感器明确报错时，采样应用可以传 `NULL`，立即撤销旧值；缓存为空，或超过 **500 ms** 没更新，回答请求时就使用 `NA`。

这让主控能够区分：**节点还能通信，但某一路传感器当前没有有效数据。**

## 三、F767 怎样向节点取数据

主控逻辑在 `STM32F767_Hub/User/App/app_hub.c`，使用两条独立串口链路。

### 1. 先探测节点

初始化后，主控先向对应节点发 `PING`。下面数值只是协议示例：

```
PING,1,1
```

节点 1 检查编号属于自己，并确认没有正文，然后回答：

```
PONG,1,1
```

主控收到匹配的回复后，把这条链路标记为已经探测成功，之后改为请求数据。

### 2. 再发送 GET 请求

例如：

```
GET,1,2
```

节点立即检查缓存，拼出响应。以下数据仅为演示：

```
DATA,1,2,IMU_RAW ms=1234 AX=100 AY=200 AZ=16000 GX=1 GY=-2 GZ=0|ADC raw=2048 mv=1650
```

节点 2 的响应示例是：

```
DATA,2,2,ENC count=12|TOF mm=256
```

正文中的 `|` 分隔两路记录。如果测距不可用，则可能返回：

```
DATA,2,3,ENC count=12|NA
```

**收到 GET 时只是读取缓存，因此回复包含的是各路最近的样本，不保证它们在同一时刻采集。**

### 3. 用序号匹配请求和响应

协议格式是：

```
类型,节点号,序号[,正文]
```

每条链路分别维护序号，发送新请求前递增。节点将收到的序号原样返回。

主控会检查节点号、序号、响应类型和到达时间，避免把旧响应当成当前请求的回答。序号是通信请求编号，**不是传感器的采样编号**。

## 四、主控的轮询和超时怎样实现

每条链路主要保存三个状态：

21:51

| 状态      | 作用                       |
| --------- | -------------------------- |
| `enabled` | 这条链路是否启用成功       |
| `waiting` | 是否正在等待一个请求的响应 |
| `probed`  | 是否已经收到过合法 PONG    |

21:51

运行规则是：

1. 每条链路约 **100 ms** 发起一次请求，两路起始时间错开约 **50 ms**。
2. 未探测成功时发 `PING`，成功后发 `GET`。
3. 发出请求后进入等待，同一条链路不会同时发第二个请求。
4. 在 **75 ms** 响应窗口内收到匹配回复，结束等待，并转发给电脑。
5. 超时则打印 `TIMEOUT`，结束本次等待，下个周期继续请求。

这里有个实际行为：**一旦探测成功，后续超时不会自动把 `probed` 清掉。** 因此恢复询问时仍然发 GET，而不是重新从 PING 开始。当前也没有独立的“离线后停止询问”状态。

## 五、串口底层怎样支撑这个流程

公共协议代码在各工程自己的 `User/Comm/link_uart.c` 中，已经不再依赖之前跨工程包含头文件的写法。

### 接收在中断里完成

每次启动接收 1 个字节，字节到达后进入 HAL 回调，再交给 `link_uart_on_rx()`。

底层会：

- 将合法 ASCII 字符追加到行缓冲。
- 忽略回车 `\r`，遇到换行 `\n` 发布完整行。
- 对超长、非法字符或缓冲被占用的行，丢弃到下一次换行。
- 记录完整行的到达时间，供主控判断是否超时。

内部只保存一行待处理数据，**不是多帧队列**。

### 命令处理在主循环里完成

主循环调用 `link_uart_take()` 取走一行，再用 `link_parse()` 解析。

F103 的 `app_node_link_run()` 只处理发给本节点、且没有正文的 PING 和 GET。F767 的 `app_hub_run()` 则检查响应是否符合当前等待的请求。

这样将“及时收字节”和“处理业务”分开，避免在接收中断中执行采样或整套应答逻辑。

### 发送和输出

`link_uart_send()` 为文本补上换行，再通过 HAL 阻塞发送，超时参数为 30 ms。

F767 对合法响应的处理是：**通过 USART1 原样转发给电脑**。当前不是将四路数据解析成统一数值结构后再融合计算，而是汇集并转发文本帧。

## 六、板间实际使用的通信接口

相关串口均配置为 **115200、8N1**。源码对应关系如下：

21:51

| 链路       | F767 端                 | F103 端                |
| ---------- | ----------------------- | ---------------------- |
| 节点 1     | USART2：PD5 TX、PD6 RX  | USART2：PA2 TX、PA3 RX |
| 节点 2     | USART6：PC6 TX、PC7 RX  | USART2：PA2 TX、PA3 RX |
| 主控到电脑 | USART1：PA9 TX、PA10 RX | —                      |

21:51

板间需要 TX 接对方 RX、RX 接对方 TX，并共地。上述是源码映射，不是本次实测接线。直连前还要核对 F767 底板跳帽和扩展模块，避免这些引脚已接到其他收发电路或外设。

## 七、这套项目具体用了哪些实现方法

核心不是某一个复杂算法，而是几种方法组合起来：

- **分层封装**：驱动负责访问外设，采样应用负责调度，节点通信负责应答，主控负责轮询与转发。
- **采样缓存**：采样独立运行，GET 直接读最新值，避免请求到来才等待一次完整测量。
- **时间戳有效性检查**：样本超过 500 ms 不再作为有效值返回。
- **请求—应答协议**：用节点号找到目标，用序号匹配响应，用换行划分帧。
- **裸机状态机**：通过时间和状态变量分步运行，而不是一直阻塞等待节点回答。
- **中断接收、主循环处理**：中断收字节，主循环做解析与业务。

## 八、当前实现的边界

目前代码已具备上述结构，但还不能据此认定整套硬件已经跑通。需要特别关注：

1. **75 ms 超时和阻塞操作的配合。** 节点 I²C 或日志发送耗时过长，可能让主控误判超时。
2. **传感器恢复仍不完善。** ADC、ToF 停采后可能持续返回 NA；IMU 虽有重试，之前发现的 I²C 总线恢复问题仍需处理。
3. **串口接收不是队列。** 主循环不及时取走完整行时，后续行可能被丢弃；重新启动接收的返回值也有被忽略的路径。
4. **这是最新值采集，不是同步采样或无损记录。** 中间样本会被新样本覆盖，四路数据也不是同一时刻的快照。

整个项目可以概括为：**两块 F103 独立采集并缓存，F767 按周期请求，节点返回带编号和序号的数据帧，F767 验证后转发到电脑。** 本次只读取和分析了本地代码，没有修改、提交或推送。
