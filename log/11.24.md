旋转编码器的驱动
先把TIM8硬件技术清零，然后启动两个编码器输入通道

读取16为硬件技术， 用模 65536 的差值处理初步回卷，在扩展到32位

为什么要处理回卷？例如硬件正向从 `65535` 变成 `0`，实际只前进了 **1**；反向从 `0` 变成 `65535`，实际只后退了 **1**。驱动通过模 65536 的差分，把这两种情况还原为 `+1` 和 `-1`。

这个方法要求：**两次读取之间，真实计数变化不能超过半个计数范围**，否则无法区分是正向大幅移动还是反向移动。软件累计值也不是无限的，最终仍受 32 位范围限制。

```c
uint16_t wrapped_delta = (current_count - precious_count);// 用模 65536 的差值处理初步回卷。
int32_t count_delta = wrapped_delta;// 扩展到 32 位，便于还原有符号增量。
```

```c
// 将 16 位差值还原为跨越计数器边界时的有符号增量。
if (wrapped_delta >= 0x8000U)
{  // 最高位为 1 时按负增量处理。
    count_delta -= 0x10000L;  // 将 16 位回卷差值还原为负数。
}  // 结束负增量转换。
```

然后保存计数

应用层就是检查然后读

你的旋转编码器使用的是 **TIM8 硬件编码器模式**，不是用外部中断逐个判断脉冲。整体流程是：**A/B 两相信号进入 TIM8，硬件自动加减计数，驱动读取并累计，应用定时通过串口输出。**

下面结合本地 `STM32F103VET62` 的当前代码讲解。

### 1. 外设层：让 TIM8 接收 A/B 信号

配置在 `Core/Src/tim.c` 的 `MX_TIM8_Init()` 中。

11:59

| 配置       | 当前值                  |
| ---------- | ----------------------- |
| A 相输入   | PC6，TIM8_CH1           |
| B 相输入   | PC7，TIM8_CH2           |
| 编码器模式 | `TIM_ENCODERMODE_TI12`  |
| 计数范围   | 0～65535，16 位循环计数 |
| 输入分频   | 不分频                  |

11:59

A、B 两路是相位相差约 90° 的方波。正转和反转时，两路信号的先后顺序相反，TIM8 据此决定计数器加一还是减一。

你使用的 `TI12` 模式会在两路有效跳变上计数，**一个完整 A/B 周期对应 4 个计数**。但“一格”或“一圈”对应多少计数，还要看编码器本身，不能直接认定转一格就加一。

### 2. 驱动初始化：清零并启动

在 `User/Drivers/encoder.c` 中，`encoder_start()` 第 7–13 行主要做三件事：

1. 将 TIM8 硬件计数器清零。
2. 将上次计数和软件累计值清零。
3. 调用 `HAL_TIM_Encoder_Start(&htim8, TIM_CHANNEL_ALL)`，启动两个通道。

**启动后，即使主循环正在处理 ToF，TIM8 也会继续自动计数。** CPU 不需要对每个边沿执行一次程序。

### 3. 驱动读取：把 16 位循环计数变成累计值

`encoder_read_count()` 第 15–35 行不是直接返回 TIM8 的值，而是：

- 读取当前硬件计数。
- 与上一次计数相减，得到这段时间的增量。
- 处理 16 位回卷。
- 将增量加入软件累计值，然后返回累计值。

为什么要处理回卷？例如硬件正向从 `65535` 变成 `0`，实际只前进了 **1**；反向从 `0` 变成 `65535`，实际只后退了 **1**。驱动通过模 65536 的差分，把这两种情况还原为 `+1` 和 `-1`。

这个方法要求：**两次读取之间，真实计数变化不能超过半个计数范围**，否则无法区分是正向大幅移动还是反向移动。软件累计值也不是无限的，最终仍受 32 位范围限制。

### 4. 应用层：每 10 ms 读取，每 100 ms 打印

`User/App/app_encoder.c` 设置了两个周期：

```
sample_period_ms = 10;
log_period_ms = 100;
```

`app_encoder_run()` 在主循环中不断被调用，但只有到期才执行对应操作：

- 每约 **10 ms** 调用一次 `encoder_read_count()`，更新累计计数。
- 每约 **100 ms** 输出一次 `ENC count=...`，也就是串口约 **10 Hz**。

所以要区分三件事：**硬件实时计数、软件每 10 ms 读取、串口每 100 ms 显示**。串口打印慢，不代表中间的脉冲没有被计入。

输出的 `count` 是从启动清零以来的**累计计数**，不是本轮增量，也不是角度或转速。程序没有定义顺时针一定为正，实际正负方向取决于 A/B 接线和编码器相序。

### 5. main 怎样串起整个流程

`Core/Src/main.c` 先调用 `MX_TIM8_Init()` 配置硬件，再调用 `app_encoder_init()` 启动驱动。

主循环中先执行 `app_encoder_run(now_ms)`，再执行 `app_tof_run(now_ms)`。如果 ToF 的 I²C 通信或阻塞串口耗时较长，会推迟下一次软件读取，但**不会直接停止 TIM8 计数**。











激光测距模块的驱动和应用

你的测距代码按 **VL53L0X 激光飞行时间（ToF）传感器**编写。整体流程是：**通过 I²C 初始化芯片，启动连续定时测距，程序定期检查结果，再将有效距离通过串口输出。**

与编码器不同，距离不是 STM32 根据脉冲自行计算的，而是传感器内部完成测量，STM32 读取结果。

### 1. 各层代码分别负责什么

| 文件                                    | 职责                                 |
| --------------------------------------- | ------------------------------------ |
| `Core/Src/i2c.c`                        | 配置 STM32 的 I²C2 外设和引脚        |
| `ThirdParty/vl53l0x/`                   | 厂商库，处理芯片配置、校准和测量     |
| `ThirdParty/vl53l0x/vl53l0x_platform.c` | 将厂商库的读写操作接到 STM32 HAL     |
| `User/Drivers/tof.c`                    | 封装启动、检查和读取距离的接口       |
| `User/App/app_tof.c`                    | 安排轮询周期、判断错误并输出串口日志 |

12:13

下面按程序实际执行顺序说明。

### 2. 先建立 I²C 通信

你的配置是 **I²C2、100 kHz**：

- `PB10` 接模块 SCL。
- `PB11` 接模块 SDA。
- 两路为复用开漏，需要模块自带或外部上拉电阻。

VL53L0X 默认的 **7 位地址是 `0x29`**。你的驱动将地址左移一位，保存为 HAL 使用的 `0x52`；读写方向由底层通信处理，不要把这两个数误认为不同的设备地址。

当前代码没有控制 XSHUT 关断脚，也没有使用模块的中断引脚，因此依赖模块上电后已处于可工作状态。

### 3. 驱动初始化：`tof_start()`

`User/Drivers/tof.c` 中，启动时依次完成：

1. **绑定通信接口**：指定 `hi2c2` 和设备地址。
2. **检查型号**：读取 `0xC0` 寄存器，要求返回 `0xEE`；通信失败或型号不符都会启动失败。
3. 调用 `VL53L0X_DataInit()` 和 `VL53L0X_StaticInit()`，完成库和芯片的基础配置。
4. 执行参考 SPAD 管理、VHV 和相位参考校准，为正常测距做准备。
5. 设置为**连续定时测距模式**。
6. 设置测量间隔为 **100 ms**，然后调用 `VL53L0X_StartMeasurement()`。

初始化成功后，芯片会自己周期性测量，**不是软件每次想读距离时都重新启动一次测量**。

这些初始化和校准操作是同步执行的，进入主循环前需要等待它们完成。你的代码没有显式设置单次测量的时间预算，因此不能把“100 ms 间隔”直接当成实际测量耗时。

### 4. 驱动读取：`tof_poll()`

这个函数不会一直等到测量完成，而是检查一次就返回：

1. 调用 `VL53L0X_GetMeasurementDataReady()`，检查有没有新结果。
2. 没有新结果，返回 `tof_pending`，交回主循环。
3. 有新结果，读取测量结构体。
4. 清除芯片内部的测量就绪标志，让后续结果能够正常处理。
5. 检查 `RangeStatus`：为 `0` 才取出 `RangeMilliMeter`，作为有效的毫米距离。

因此驱动向应用层返回四种结果：

12:13

| 返回状态       | 含义                           |
| -------------- | ------------------------------ |
| `tof_pending`  | 测量还没完成，稍后再检查       |
| `tof_valid`    | 得到了有效距离                 |
| `tof_invalid`  | 有测量结果，但质量或状态不合格 |
| `tof_io_error` | I²C 读写等操作失败             |

12:13

**无效距离不等于通信失败。** 通信正常时，也可能因为目标或测量条件得到无效结果，不能把它直接当作可靠距离使用。

### 5. 应用层：定时检查并打印

`User/App/app_tof.c` 设置了：

```
poll_period_ms = 10;
result_timeout_ms = 500;
```

`app_tof_run()` 每约 **10 ms** 检查一次结果，并根据状态处理：

- 有效时打印 `TOF mm=<距离>`，单位是毫米。
- 无效时打印 `TOF INVALID`，继续测量。
- 连续约 **500 ms** 都没有新结果时，打印 `TOF TIMEOUT` 并停止后续轮询。
- 通信失败时打印 `TOF I2C_ERR`，同样停止后续轮询。

有效和无效结果都会刷新“上次收到结果”的时间。因此，一直收到无效结果时会持续打印 `TOF INVALID`，不会因为它们无效就触发上述超时。

这里要区分：**芯片每 100 ms 测量一次，软件每 10 ms 检查一次；串口则在拿到有效结果后才打印距离。** 正常时距离输出预计约为 10 Hz，不是 100 Hz，也不是板上实测值。

### 6. main 怎样调用它

`main.c` 先配置 I²C2 等外设，再调用 `app_tof_init()`。进入主循环后，每轮先运行编码器应用，再运行测距应用。

虽然检查结果的逻辑不会空等新测量，但底层 I²C 事务和串口发送仍是**带超时的阻塞调用**。通信异常时，它们可能拖慢下一轮软件调度，不过不会停止 TIM8 的编码器硬件计数。
